## SOC investigation notes:

* **Tier 1 Analyst (Triage):**

* **Tier 2 Analyst (Deep Dive & Intent Verification):**

### Behavior: Failed Authentication Threshold Exceeded (T1110 / Brute Force)
* **Telemetry Sources:**
  * Authentication Logs (`security.log`) capturing repeated password failures.
  * Detection Engine Logs (`detector.py`) aggregating counts per IP address.
* **Tier 1 Analyst (Triage):**
  * **Threshold Verification:** Verify whether the alert originated from a single host or a centralized authentication service where high failure volume is expected.
  * **Source IP Context:** Examine source IP `172.18.0.5` to determine if it belongs to an internal subnetwork, a VPN pool, or an external proxy.
  * **User Typo vs. Automation:** Check if failures are spread across multiple user accounts or targeted at a single account to distinguish typos from credential stuffing.
* **Tier 2 Analyst (Deep Dive & Intent Verification):**
  * **Time Window Assessment:** Investigate whether failures occurred within seconds (automated brute force) or over hours/days (legitimate user forgetting password).
  * **Post-Failure Activity Correlation:** Check subsequent log timestamps for successful logins originating from `172.18.0.5` to verify if compromise actually occurred.

### Behavior: Explicit Network Scan Record Detected (T1046 / Network Service Discovery)
* **Telemetry Sources:**
  * Network/Security Logs (`security.log`) containing `Network scan detected` strings.
  * Dashboard Alerts (`lab1a-dashboard`) mapping log entries to MITRE STIX objects.
* **Tier 1 Analyst (Triage):**
  * **String Validation:** Confirm if the log string is generated by an authorized internal scanner (e.g., vulnerability manager) or an unknown source IP `172.18.0.7`.
  * **Target Port Review:** Inspect targeted ports (`22, 80, 443, 3306`) to identify reachable exposed services on the network segment.
* **Tier 2 Analyst (Deep Dive & Intent Verification):**
  * **Packet-Level Verification:** Validate raw traffic flows in EDR/NetFlow logs to ensure actual TCP handshakes or SYN packets occurred rather than relying solely on log string generation.
  * **Preceding Activity Correlation:** Correlate scanning timestamps with subsequent authentication or exploitation attempts from the same source IP.

### Behavior: Detector Script Parameter Analysis (`detector.py`)
* **Telemetry Sources:**
  * Source code analysis of `detector.py`.
  * Log polling interval configuration (`SCAN_INTERVAL_SECONDS = 5`).
* **Tier 1 Analyst (Triage):**
  * **Rule Parameter Review:** Identify static parameters (`FAILED_PASSWORD_THRESHOLD = 3`, polling interval = 5s).
  * **Candidate Finding Scope:** Recognize that deterministic rules only produce candidate alerts, requiring human validation.
* **Tier 2 Analyst (Deep Dive & Intent Verification):**
  * **Rule Limitation Identification:** Document absence of time windows in failure counting and reliance on text matching over network flow analysis.

### Behavior: Controlled Experiments & Threshold Sensitivity (C1–C4)
* **Telemetry Sources:**
  * Modified `security.log` files during synthetic injection testing.
  * Real-time dashboard updates reflecting updated detector scan cycles.
* **Experiment Observations:**
  * **C1 (Below Threshold):** Reducing failures for `172.18.0.5` to 2 dropped total active findings from 2 to 1, confirming rigid enforcement of `FAILED_PASSWORD_THRESHOLD = 3`.
  * **C2 (IP Distribution):** Distributing 3 failures across 3 distinct IPs (`172.18.0.5`, `172.18.0.6`, `172.18.0.8`) yielded 0 brute-force alerts, proving detector groups strictly per-IP without subnet aggregation.
  * **C3 (New IP Injection):** Appending 3 synthetic failures for `192.0.2.55` generated a new High-severity finding on the next 5-second scan cycle.
  * **C4 (Additional Scan String):** Adding a synthetic scan log for `192.0.2.77` incremented total findings to 3 via direct string matching.
